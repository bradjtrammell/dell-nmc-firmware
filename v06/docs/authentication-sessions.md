# v0.6 native authentication and session enforcement

**Status: freestanding security/session core and read-only API/UI status reporting are implemented. Production login is NOT enabled.** This is new independent firmware code on `dev`, not Dell firmware authentication. It is not operating on the live H910P.

## Implemented native session protections

`include/ou_auth.h`, `src/auth.c`, and `tests/test_auth.c` provide a bounded C99 session engine for the existing ARM7 research target:

- Maximum **four** independently revocable sessions; no heap allocation, hardcoded credentials, default accounts, insecure password fallbacks or platform networking dependencies.
- Viewer (read-only), operator (configuration writes), and administrator (power, firmware update, user administration) roles enforced by a centralized permission function.
- **256-bit session token and independent 256-bit CSRF secret**, both generated by a required, externally supplied, hardware-qualified CSPRNG; all-zero or reused credentials are refused. The module does not claim that deterministic test randomness constitutes cryptographic entropy.
- Every mutation requires a valid session, matching CSRF secret, correct role, and a strictly increasing request counter. Replayed, zero, or stale mutation IDs are rejected.
- **15-minute idle timeout**, **8-hour absolute session timeout**, 32-bit monotonic clock rollover handling, logout, administrative revoke-all, and fixed-memory secret erasure.
- Five consecutive failed credential attempts cause a **60-second global lockout**. The production integration must also add per-source/account limits to reduce denial-of-service risk, a reset policy, audit events, and session lifecycle management across time-source discontinuities.
- An `ou_auth_config_gate` authorization callback matches the existing `ou_config_authorize_fn` signature. It can deny unprivileged, missing-CSRF and replayed configuration requests *before* the transactional apply/persist system is invoked. This callback does not grant physical network or flash qualification.

## Mandatory external providers — not mocked in production

The engine does **not** contain password hashes, a password hashing algorithm, network/TLS transport, session cookie parser, or an RNG implementation. The real board adapter must supply and qualify:

1. **Cryptographically secure hardware/OS randomness** with health checks and distinct token/CSRF generation. The test's deterministic random provider is strictly for simulated verification.
2. An authenticated **HTTPS** transport with enforced modern TLS, browser cookies bearing `Secure`, `HttpOnly`, `SameSite`, secure cookie scoping, and correct anti-CSRF binding. The core's `encrypted_transport` bit must be set only by the qualified TLS integration.
3. Credential provisioning/storage and a vetted, password-hardened, constant-time **password KDF verification** implementation with algorithm/version and parameter agility. No default password. Secrets must be protected at rest and rotated through an authenticated interface.
4. A trustworthy monotonic clock and a serialized request dispatcher. The core is not thread-safe and must be called from the single-threaded event loop or under a verified lock.
5. A role-aware audit log that never stores raw usernames with passwords, tokens, CSRF secrets, or private key material. Security controls must be evaluated for network isolation and device-resource constraints.

### API/UI boundaries

`GET /api/v1/security/capabilities` reports **`sessionEngineCompiled:true`** but returns false for login availability, TLS/entropy/credential store qualification and mutation authorization. The Access Control UI displays that honest state, session policy, and unavailable operator controls. The host simulator remains loopback-only and read-only; every `POST` / `PUT` / `PATCH` / `DELETE` still returns **405** and no HTTP login handler exists.

When real hardware providers become available, the native service should only activate the login/authorization pipeline after all qualifications pass together. Until then, a tested data structure is not an authenticated management endpoint.

## Verification

The test suite runs permission/role enforcement, token uniqueness and rejection, empty/invalid entropy, failed provider qualifications, lockout timing, session count exhaustion, idle and absolute expiry, monotonic rollover, CSRF rejection, replay denial, logout/revocation, and configuration-write authorization. AddressSanitizer/UBSan and the freestanding **big-endian ARM7** compile/link are mandatory CI gates. Browser behavior and host HTTP checks assert a truthful disabled-login state and the absence of default credentials and mutation routes.

**Explicitly still outstanding:** real secure boot/flash and recovery qualification, hardware entropy and credential store, TLS listener and cookie parser, real role administration, signed GitHub release verification and safe updater, device-resident UI, and UPS control/scheduling/notifications. None of these is declared done by this module.
